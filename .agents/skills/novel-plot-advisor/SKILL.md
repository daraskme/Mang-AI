# novel-plot-advisor

ユーザーが書きたい核と、想定読者へ届く企画構造の交点を探す。テンプレは規則ではなく、読者期待を説明するためのモデルとして使う。

## 1. 境界

- 明示された相談・壁打ちでだけ使う。
- ユーザーが指定していないリポジトリ内のplot、draft、台帳を勝手に読まない・書き換えない。
- 小説本文は書かない。タイトル案、ログライン、あらすじ案、箇条書きの構成案までは扱う。
- 執筆へ進む場合は `long-novel-orchestrator` へ成果物を引き継ぐ。
- novel-Standardへ採用する場合は、合意した企画を `work/plot.md` の「読者への約束・投稿戦略ブリーフ」、キャラ案を対応するcharacter-sheet、局所展開をscene-cardへ落とす更新案として示す。相談だけの依頼では実ファイルを変更しない。

novel-Standard作品を対象にする場合、`AGENTS.md` と `guidelines/04-structure-and-plot.md` が上位規約である。本Skillの市場仮説や代替構造で上書きせず、規約適合の診断と、規約外の一般的な選択肢を分けて説明する。矛盾を見つけても、相談だけの依頼でガイドラインを変更しない。

## 2. 相談モードを選ぶ

| モード | 最初に読む | 必要に応じて |

| 新企画・ネタ出し | [相談手順](references/consultation-playbook.md) | [テンプレ類型](references/template-catalog.md)、[サイト比較](references/site-meta.md) |
| 既存プロット診断 | [相談手順](references/consultation-playbook.md)、[読者への約束](references/reader-promise-framework.md) | [テンプレ類型](references/template-catalog.md) |

必要な資料だけを段階的に読む。

## 3. 診断の原則

1. 目的、想定読者、尺、書きたい核を区別する。
2. 企画を「主人公の立場／変化／想定する読後報酬」の一行に仮置きする。
3. 読者が入口で受け取る約束と、実際のプロットが返すものを照合する。
4. 類型を使う場合は主となる快感原理を特定し、掛け合わせ数や比率を固定ルールにしない。
5. 強み、優先課題、具体案、代償の順で返す。
6. チェックリストを合格基準にせず、目的に効く修正だけを提案する。

「序盤3話で小さく返す」「各話末に次の報酬を置く」等は、報酬駆動型の商業Web連載で有力な初期仮説である。ミステリー、ホラー、文芸、スローな没入型では、謎、恐怖、情緒、関係変化、語りの魅力が約束になり得る。作品の意図を壊して一律適用しない。

## 4. 市場情報を扱う

投稿サイト、ランキング、コンテスト、読者属性、タイトル上限、数値目標は変動情報として扱う。重要な意思決定では、保存資料の日付にかかわらず最新の公式ヘルプ・ランキング・要項を `web_search` と `web_fetch` で確認する。

- 公式仕様とランキング観測を分ける
- 非公開アルゴリズムは推定と明示する
- 単一時点の上位構成を市場全体の因果として断定しない
- 古い数値を現在の撤退基準や目標値へ流用しない

最新確認ができない場合は、時点付き仮説として提示し、断定を避ける。

## 5. 出力

相談内容に応じて、次を必要な分だけ返す。

- 企画の一行要約と、読者へ約束する体験
- 強みと、直すと効く順の課題
- 方向性の異なる複数案。三案に固定しない
- 各案の利点、リスク、想定読者、投稿先との適合
- 序盤の状態変化・報酬・未完了の圧力
- 追加検証が必要な市場仮説と出典日
- novel-Standardへ引き継ぐ場合の、plot／character-sheet／scene-card別の採用項目

「勝てる／勝てない」を断言せず、前提条件と検証可能な指標を示す。

## 6. R18と他Skill

R18企画の関係性・構成レベルは相談できるが、性描写の本文設計は行わない。成人向け本文へ進む場合は、通常の執筆ワークフローから `novel-write-r18` の適用条件に従う。本文のAI的特徴診断や自然化改稿は、本Skillの管轄外とする。
