# 漫画制作の方針 — A1・Gemma 4・Krea 2

更新：2026-10-06。利用者が指定した制作方針を保存する正本。Mang-AIの漫画制作エージェントは`manga_workflow_guide`で着手時と工程変更時に本書を参照する。実装済みの操作と、未検証・今後の要件は末尾で区別する。

## 役割と制作単位

- **A1 4B**：司令塔。依頼を整理し、現在の工程・確定事項・未決事項を読み、Gemma 4へ段階ごとの作業を依頼する。結果を検査・保存し、生成・修正・文字入力ツールを操作する。
- **Gemma 4 Ortenzya**：物語、人物、背景、ページ配分、コマ内容、漫画・動画用の自然言語プロンプトを担当する。全工程を一度の長い出力で済ませず、保存済みの前工程を受け取って次を作る。
- **Krea 2 / Kroma**：確定した作画指示と、利用者が指定したモデル・キャラクターLoRA・Style LoRAで絵を生成する。
- **利用者**：作品の意図、使うモデル・LoRA、生成結果への修正指示を決める。指示済みの制作を、工程ごとに同じ許可を取り直して止めない。新しい重要設定や指示と矛盾する変更は未決として扱う。

作品を一つのまとまりとして管理し、その下にページ・コマ・生成版・編集版・書き出しを置く。同じ作品を再開したら、会話の記憶だけで設定を作り直さない。

## 1. 全体の流れ・設定・人物・背景を先に決める

Gemmaへ渡す入力は、利用者の依頼、確定設定、希望する尺、画風、指定LoRA、変更してはいけない点。出力には次を含める。

1. 何が始まり、何が起き、どう終わるか。読者へ情報を見せる順と、感情が変わる箇所。
2. 登場人物の固定ID、外見、衣装、体格、話し方、関係、目的、持ち物。キャラクターLoRAのID・トリガーは人物へ紐づける。
3. 場所の固定ID、構造、つながり、家具・扉・窓・特徴物、時間帯と光。別アングルになっても場所を識別できる目印。
4. 場面カード：場所、時刻、登場人物、開始時の状態、見える行動、終了時の状態、次の場面へ移る理由。
5. 未決事項。Gemmaが補った案は提案として保存し、既に確定した事実と混ぜない。

**家の場面の例**：リビングの会話と玄関での見送りを別の場所・場面として登録する。同じ家に属すること、リビングから廊下を通って玄関へ移ること、誰が外へ出て誰が家に残るかを固定する。玄関では靴・鞄・扉の開閉・内外の立ち位置・声を掛ける相手を引き継ぐ。ページをまたいだだけで服や鞄が変わったり、玄関が別の家になったりしない。

設定資料は「計画」、採用済みのページに現れた事実は「既出記録」として分ける。変更・却下の理由も保存し、却下案を次の生成で復活させない。

## 2. ページ数・場面配分・コマ割りを決める

全体の流れから必要なページ数を提案する。利用者のページ数指定があれば優先し、台詞を詰め込んで帳尻を合わせない。現在の標準レイアウトは1ページ2〜4コマ、右から左の日本漫画。ページをめくる前後の情報差も設計する。

各ページに、ページの役割、対象場面ID、開始・終了状態、コマ割り、読順、見せ場、台詞・地の文の量、次ページへのつなぎを割り当てる。各コマは、人物、場所、1時点の行動、視点・距離、画面内の位置関係、台詞の話者・相手、文字を置く余白を持つ。

「リビングで会話し、立ち上がり、移動して玄関で見送る」を一コマへ詰めない。必要な瞬間を分ける。手渡し・接触などは、動作の前後と誰のどの手かを確かめる。見せる必要のない移動は省略できるが、場所が変わったことを読者が理解できる絵を置く。

この段階で実際の台詞を仮配置したネームとして通読し、絵と文字の量、話者、読順、背景の連続性を確認する。

## 3. Krea 2向けの構造化プロンプトを作る

ページごとに構造化データを保存し、Gemmaがそこから作画用の自然言語を組み立てる。JSONのキー名をKreaが特別に理解するという前提は置かない。構造はMang-AIの管理用であり、画像モデルに渡す本文は具体的な自然言語にする。

Krea公式技術報告の根拠は、詳細な自然言語キャプションによる条件付けと、依頼の意図を保つプロンプト拡張である。**公式が漫画用JSON書式、タグ順、固定の語数、特定の漫画レイアウト記法を規定しているわけではない。** 以下はMang-AIの運用規則として定める。

| 階層 | 保存する情報 |
|---|---|
| 作品共通 | 確定した画風、人物・衣装、背景、描画モデル、Style LoRA |
| ページ | ページID、場面ID、役割、コマ割り・読順、共通の時刻・光、ページ全体の作画ブリーフ |
| コマ | コマID、人物ID、場所ID、1時点の動作、構図・距離・視線、背景の固定物、手・小物の状態、文字用余白、英語の作画本文 |
| 文字 | 日本語の台詞・地の文、話者、表示順、入力先コマ、縦横方向。作画本文とは別に保存 |
| 生成条件 | モデルID、LoRA IDと強度・有効状態・トリガー、seed、サイズ、steps等。文章へ埋め込まず実行引数にも設定 |

作画本文は、場面と主題 → 人物の外見・衣装と位置 → 一瞬の動作・表情 → 背景・小物 → 構図・光・画風 → 文字用の余白、を基本に、必要な情報だけ具体的に書く。順序は固定のモデル仕様ではない。矛盾する構図、抽象的な感情だけの指示、人物数の曖昧さ、同時には描けない時系列を取り除く。利用者の意図にない小物・行為・別の画風をプロンプト拡張で追加しない。

人物と背景の固定情報は、モデルが各生成で以前の画像を覚えていると想定せず、対象コマに必要な範囲を再投入する。人物・場所の`visualDescription`に簡潔な英語の固定説明を保存し、作画ツールが対象IDに対応する説明を各コマの実行プロンプトへ付加する。旧データでは`appearance / description`を使う。「同じ人物」だけで衣装の再記述を省かない。合計4000文字を超える場合は無断で切り捨てず、Gemmaで短くする。

トリガーは登録情報を使い、架空のトリガーを推測しない。LoRA未指定なら選択を確認し、指定済みなら保持する。利用者の指定なしに別LoRAへ差し替えたり、強度を変えたりしない。

**現在の生成単位**：ページ全体の構造化計画からコマ別のプロンプトを取り出し、Kreaで各コマを生成して、Mang-AIがページのコマ枠へ合成する。これによりコマ割りと文字が編集可能なまま残る。ページ一枚を丸ごと画像モデルへ描かせる方式は、別の生成モードとして実装・検証できるまで対応済みと扱わない。

## 4. 指定モデル・LoRAで生成する

A1が保存済みの計画と生成条件を読み、モデル・LoRAの存在と互換性を検査してから作画を開始する。人物LoRAとStyle LoRAは役割を区別して記録する。モデルの切替や不足ファイルを既定値への置換で隠さない。

生成前にGPU・RAMへ負荷が掛かることを通知する。元のプロンプト、モデルとLoRAの実行値、seed、ジョブID、出力先を保存する。完了した画像だけをページへ反映し、処理中・失敗・未生成を完成扱いしない。

## 5. 生成画像を見ながら修正し、文字を入れる

利用者の修正指示を、対象ページ・コマ・版、変える点、残す点へ分けて保存する。画像を見られる設定のモデルで確認した場合だけ「画像を確認した」と記録する。プロジェクター未接続や画像入力未対応なら、利用者の指摘とツールの結果に基づく判断だと区別する。

- **構図・人物・背景・動作の変更**：Gemmaへ該当コマと必要な設定だけ渡してプロンプトを改稿し、対象を再生成する。A1も利用者の具体的な指示に沿った小さな修正を行える。元のプロンプトと画像を残す。
- **局所の不要物・欠損など**：IOPaintでマスクを指定し、補完結果を確認してから採用する。現在のLaMa補完は文章による指示編集ではない。意味のある新要素の追加など、LaMaで扱えない変更はプロンプト修正・再生成へ戻す。
- **台詞・地の文・吹き出し**：専用の文字入力・吹き出しツールを使う。基本は縦書き、上から下、列は右から左。台詞の誤字だけなら絵を再生成しない。地の文はcaption、通常台詞はspeechとして区別する。

Kreaへ台詞そのものを描かせない。現在の標準は、Kreaが絵と**空の吹き出し**を一緒に描き、源暎アンチックの日本語文字を後から重ねる方式。`manga_render(balloonMode:generated)` で、台詞の本数・話者・配置に合わせた空の枠を生成へ指示する。既存の吹き出し配置があればその座標、未配置ならコマ上部の右→左を目安にする。顔や手を隠さず、縦書き用の内側余白を確保する。無言コマには不要な枠を足さない。

完成画像ごとに生成方式を保存する。`manga_letter` の `shape:auto` は空吹き出しを生成したコマでは枠を重ねず、文字だけを描く。手動で `shape:art`（文字だけ）または `shape:overlay`（枠と尾も描く）を選べる。GUIの「吹き出しの枠」でも変更できる。旧画像と保存済み文字は一括変換しない。従来方式の新規作画は `balloonMode:overlay`。

生成した枠の形・位置・本数は厳密に保証されない。自動検出や自動フィットは未実装なので、生成後に画像を確認し、文字のx/y/width/height/fontSizeを枠の内側に合わせる。枠と尾は画像の一部で文字ツールでは移動できないため、必要ならIOPaintや再生成で直す。吹き出しの尾・話者・読順・はみ出しを確認し、収まらないからといって無断で台詞の意味を削らない。

空吹き出しの生成指示には日本語の話者名や台詞本文を転記しない。名前まで絵に描かれる場合がある。空の指定でも疑似文字が混ざることがあるため、文字入力の前に内部を確認し、混入時はIOPaintで文字部分をマスクして消し、枠の輪郭を保った結果を採用する。確認できないまま上から本来の文字を重ねない。

2026-10-06の実機試験では、Gemmaのプロンプト＋Kroma/漫画Style LoRAで1コマを生成。初回は話者名と疑似文字、余分な枠が混入した。話者名を画像指示から除き、輪郭と尾だけを描く指示へ修正した同seedの2回目で、空の枠1つを目視確認した。源暎アンチックの縦書き文字を別合成し、位置を手動調整して確認した。1場面の結果であり、全ての生成で空欄・本数・位置が保証されるわけではない。

修正後は、そのコマだけでなく前後ページとの衣装・位置・小物・光・因果のつながりを確認する。機械検査の合格だけで絵の品質確認を済ませたことにしない。再生成を自動で無限反復せず、具体的な不具合と利用者の修正方針に基づいて対象を絞る。

## 6. 保存・再開・書き出し

各工程の成果物には版番号と参照した設定の版を残す。設定変更時は影響するページ・プロンプトを要確認へ戻し、以前の絵を黙って現在の設定の完成品にしない。利用者の手動編集は保持する。

再開時は、作品の現在状態 → 未完了の工程 → 今回のページ計画 → 関連する人物・場所 → 直前・直後のページ、の順に必要部分だけ読む。全作品を毎回コンテキストへ詰め込まない。

書き出し前に、全ページの作画有無、文字の表示、読み順、指定LoRAの使用記録、修正指示の未処理項目を確認する。PNGなどの閲覧用と、再編集できるプロジェクト・SVGを保存する。

## GPUの工程順

`A1常駐 → Gemmaで設定・ページ計画・プロンプト → 成果物保存 → Gemma解放 → Kreaで作画 → 必要な編集 → Gemma/A1で修正判断 → 必要な対象だけ再生成 → 文字・書き出し`

A1は他工程の開始時も解放しない。大きなQwenはコーディング用途だけで、漫画の通常プロンプト作成には使わない。画像・動画・キャプション・学習・Qwenを同時に無制限に積まず、実行中ジョブと空き容量を見て切り替える。仮想マシンは利用者が停止する。Mang-AIが他アプリを勝手に終了しない。

## 実装との対応

| 工程 | 操作・保存先 |
|---|---|
| 方針の参照 | `manga_workflow_guide`。全体またはsettings/pages/prompts等の一工程 |
| 作成・再開 | `manga_create` / `manga_status`。DSHセッションごとの作品 |
| 初回の段階制作 | `manga_plan(stage:all)`。設定→配分→各ページのプロンプトを別々にGemmaへ依頼し、その都度保存。中断時は保存済み工程から再開 |
| 工程単位の修正 | `manga_plan(stage:settings / pages / prompts)`。promptsはpageId指定。上流の変更時に下流を要更新へ戻す |
| 保存する計画 | 作品の`production.settings / pages / prompts`。各入力・Gemma出力は作品フォルダの`requests/`、版はSQLite履歴 |
| 作画 | `manga_render`。セッションで選んだモデル・LoRAと強度、seedをジョブに保存 |
| 修正・文字 | `media_edit` / `media_edit_commit`、`manga_letter`、同じ制作スペースの編集GUI |
| 保存・書き出し | `manga_export`。編集用JSON、画像込みSVG、閲覧用HTML。GUIからPNG |
| 負荷と進捗 | A1常駐、共通GPUキュー、`gpu_status`、GUIの「制作の進捗」 |

ページ数の指定は`pageCount`へ別に渡す。版番号は返された`revision`をそのまま使い、A1が自分で加算しない。利用者の手動変更と競合したら上書きせずに再読込する。`all`完了後は修正依頼がない限り計画工程を繰り返さない。

2026-10-06にA1→Gemmaの3工程保存、Kroma＋漫画Style LoRAで2コマの作画、縦書き文字、SVG/HTML書き出しを実機確認した。A1を維持したままGemmaとKreaが処理後に解放されることも確認した。A1には題名の取り違え、余分な工程の再実行、画像の読順・動作の誤認があり、作品品質や指示の完全順守を保証する試験ではない。

今後の要件：人物・背景・小物の意味的な矛盾の自動監査、計画と採用済み事実を分けた完全な正典台帳、修正指示ごとの未処理項目管理。現状のID照合・版管理はこれら全ての代替ではない。コーディング用の大型Qwenは導入・設定済みで、VM停止後の実機推論を待つ。[詳細な構成・検証範囲](local-agent-architecture.md) と [導入記録](resident-model-setup.md) を参照。
