# 単独動画制作の方針 — A1 4B用

2026-10-06。MiniMax H3の単発動画・画像からの動画・複数ショットの長尺動画を扱う。画像から始める場合は [単独画像制作の方針](image-production-policy.md) へ先に渡す。

## overview — 工程と担当

`目的・尺・人物と背景 → 必要なら先頭画像 → Gemmaで動作と音の設計 → H3生成 → 動画確認・修正 → 仕上げ・保存`

A1は進行、創作用Gemma Ortenzyaは自然言語の動画プロンプト、H3は映像・音声を担当する。短い一つの動作はh3、複数ショットの接続はlongvideo。長尺という語だけでループ延長やフレーム補間を代替にしない。

| 工程 | 次の操作 | 完了の証拠 |
|---|---|---|
| prepare | provider決定、モデル/LoRA選択、先頭画像 | 尺・構成・入力画像が確定 |
| prompt | `media_prompt(provider:h3/longvideo)` | 保存されたprompt。長尺はplanの検査結果 |
| generate | `h3_generate` / `h3_longvideo_generate` → `media_job` | completed、outputPath、実際の出力情報 |
| review | 動画・音声確認、対象の修正、拡大 | 採用版と残課題 |
| save | 同じcollectionIdでまとめ、ギャラリー表示 | 作品、元動画、派生版を再参照できる |

工程ごとに `media_workflow_guide(workflow:video, section:工程名)` を読む。計画だけの依頼では生成を開始しない。

## prepare — 尺と生成経路を決める

目的、人物・外見・衣装、場所、開始状態と終了状態、動きの順序、カメラ、縦横比、尺、音声・台詞・環境音を整理する。発話の日本語は保持する。利用者が無音を指定した場合はプロンプトにも明記する。

単発H3の現行入力は124〜345フレーム・24fps、フレーム数は17k+5に調整される。長尺は最大24ショット、各1〜15秒、計画合計120秒。ショットごとの秒数は現在共通のshot_secondsで、可変尺を個別指定できるものと扱わない。完成尺はフレーム整列などで変わる。

必要なproviderを `media_service` で起動し、`media_status` でreadyを確認する。`media_model_catalog` → `media_model_select` でモデル・人物/Style LoRAと強度を固定する。h3とlongvideoでは同じモデルでもID形式が異なる場合があるため、そのproviderの一覧を使う。トリガーをGemmaへ伝え、不明なものを推測しない。

画像から動画を作る場合、既存の先頭画像、または画像制作手順で作った採用画像の絶対パスを保持する。h3はfirstFramePathとlastFramePath、longvideoはfirstFramePathを受け取る。後者に末尾画像の引数を捏造しない。

## prompt — Gemmaで時間の流れを組む

`media_prompt` のinstructionに依頼、contextに人物・場所・開始/終了状態、時間内に起こる動作、カメラ、音、トリガー、保持する点を渡す。単発は一つのショットに収め、同時にはできない動作や短すぎる尺に長い台詞を詰め込まない。参照画像は単なるパス文字列を渡しただけでGemmaが見たと扱わない。確認済みの外見情報をcontextへ記す。

長尺では最初の段落を共通設定、空行で区切った次の段落から1段落1ショット。各ショットへ開始/終了状態、つながる動作、カメラ、必要な環境音を記し、発話は原語のまま二重引用符で囲む。服装・位置・小物・光を引き継ぎ、「前と同じ」だけで説明を省かない。

保存されたpromptを `h3_longvideo_plan` に渡し、shot_seconds、段落数、計画尺を検査する。これは構文と尺の検査で、人物や動作の意味的な連続性を保証しない。検査した引数をそのまま生成へ渡す。Gemmaのnotesにある未決事項も確認する。

## generate — 入力を固定して実行する

GPU・RAM負荷を通知してgpu_statusを読む。Gemmaの結果を保存・解放してから、単発は `h3_generate`、長尺は `h3_longvideo_generate` へ進む。作品名projectTitleを付け、返されたcollectionIdを同じ作品の続き・修正版に渡す。ジョブIDと作品IDを取り違えない。

モデルに合うpreset/stepsを使う。現在の長尺既定は導入済みDaSiWa Turbo v3・8step・0.4MP。人物/Style LoRAと高速化用LoRAを区別し、蒸留済みモデルに追加の加速LoRAを重ねない。h3のベースモデルでturboを使う場合、アダプターが対応する加速LoRAを追加する。存在しないモデルや高速化方式へ無断で置き換えない。

返されたidを `media_job` で追跡し、queued/runningで再投入しない。completedと回収ファイルを確認してから出力を提示する。unknownや履歴消失は完了ではない。再接続時は元idを再照会し、エラーを解消する前に同じ高負荷処理を繰り返さない。

## review — 動き・音・仕上げの確認

動画を再生し、人物と衣装の一貫性、手足・顔、動きの順序、カメラ、ショット境界、台詞と音の有無・同期、出力尺を確認する。先頭フレームだけの確認を動画全体の確認に数えない。A1が全動画や音声を直接確認できない場合は、確認できたフレームと利用者の指摘を区別して報告する。

修正は対象のショット/時間帯、変える点、残す点をGemmaへ渡す。現在、完成した長尺の任意ショットだけを自動差し替えする機能はない。再生成範囲と既存版を残す方針を示す。動画のIOPaint補完は未対応。動画モザイクはmedia_open_editorとmedia_edit、静止画の先頭画像修正は画像制作手順を使う。

| 仕上げ | 現在の操作 |
|---|---|
| 単発H3の潜在Hires | 生成時のlatent_refine。対応upscaler、仕上がり寸法、scale/steps/strengthを指定 |
| 完成した単発H3の画素拡大 | 元ジョブidにmedia_upscale。音声を保持。新idで完了確認 |
| 長尺の潜在/画素拡大 | 生成時のlatent_upscale / upscale。完成後media_upscaleには非対応 |

長尺のlatent_upscaleは単発H3のlatent_refineと同じ短段再生成ではない。モデル未導入や適用失敗のwarningsを確認し、元解像度の動画を「Hires済み」と報告しない。導入済み方式と出力情報を根拠に選ぶ。

## save — 動画作品単位で残す

同じcollectionIdに元動画、修正版、単発H3の拡大版をまとめる。セッションにはGemmaの依頼・応答、生成条件、ショット計画、ジョブIDと回収動画が残る。`media_open_gallery` で作品単位に見せ、手動生成・進捗確認は `media_open_generator`。

採用動画のID・パス、モデル/LoRA、先頭/末尾画像、seed、指定尺と確認できた実尺、仕上げ方式、未解決の指摘を報告する。中断後は元idをmedia_jobで照会する。現在、全制作工程や任意ショットの自動再開は未実装なので、保存した入力と完了済み出力を確認してから残りの処理を決める。

## gpu — 画像から動画への順序

`A1常駐 → Gemmaで画像プロンプト → 解放 → Kreaで先頭画像 → 解放 → Gemmaで動作と音 → 保存・解放 → H3単発または長尺 → 解放 → 必要な仕上げ`

先頭画像が既にあれば画像工程を省く。Gemmaを呼ぶたびに必要な資料だけを渡す。H3の内部テキストエンコーダーと、コーディング用Qwenを混同しない。画像・動画・キャプション・学習を共通GPUキューへ順番に渡し、A1は常駐を維持する。重い処理の前に通知し、空き不足時は利用者へ必要量を伝える。VMや他アプリは停止しない。
