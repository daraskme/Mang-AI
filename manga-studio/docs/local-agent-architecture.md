# 常駐エージェントとGPU工程管理

2026-10-06の構成と確認結果。導入手順、固定リビジョンと変換内容は [resident-model-setup.md](resident-model-setup.md) に記録する。

## 役割

| 役割 | 指定モデル・環境 | 読み込み方針 |

| 司令塔・ツール操作 | NullpoLab Agents A1 4B Heretic ARA Refusals8 Q8 | Mang-AI起動中は常駐。他の工程を開始しても解放しない |
| コーディング | orcarouter Qwen3.8 Flash Next Uncensored Q8 + Strata | コーディングの間だけ使用。RAM/VRAMの実測値で起動を制御 |

利用者は、大きなQwenを使うときに自分で仮想マシンを停止する運用を選択した。他アプリや仮想マシンをMang-AIが終了する権限は与えられていない。

## 工程

漫画の詳細な制作方針は [manga-production-policy.md](manga-production-policy.md) を正本とする。全体設定と場所の連続性、ページ配分、構造化プロンプト、指定LoRA、修正と縦書き文字入力をこの順に扱う。

単独の [画像](image-production-policy.md)・[動画](video-production-policy.md)・[LoRA](lora-production-policy.md) は `media_workflow_guide` で工程ごとに読む。A1のシステム指示からこの入口へ案内する。素材収集と動画の時間変化のキャプション、H3新規学習は今後の接続範囲として明記し、Krea2学習のfamily検査で取り違えを防ぐ。

漫画：依頼整理 → 人物・場面・読み順 → 字コンテ → コマ割り・ネーム → レビュー・脚本確定 → Gemmaの作画プロンプト → モデル/LoRA選択 → Krea作画 → 縦書きの文字配置 → PNG確認 → 修正 → 書き出し。

動画：依頼整理 → 人物・開始/終了状態 → ショット計画 → Gemmaの自然言語プロンプト → モデル/LoRA選択 → H3生成 → 連続性確認 → 必要なHires・修正 → 書き出し。

各段階の成果物、選択したモデル/LoRA、プロンプト、生成結果、レビュー、未完了項目を作品単位で保存する。プロンプトの生成完了と画像/動画の生成完了を区別する。過去の成果物を残し、失敗・未実行を完了表示しない。

## メモリ制御の要件

- A1常駐分とOS用の余裕を先に確保する。
- 大規模処理は共通の待ち行列で管理し、工程切替時に前の大規模モデルを解放する。
- 実行中のジョブを別の工程が勝手に停止しない。中止は所有するジョブへ行う。
- 空きRAM/VRAMが足りない場合は必要量・現在量・待機理由をGUIとツールへ返す。
- プロンプトを保存してからGemmaを解放し、画像/動画モデルを読み込む。
- 生成・学習の高負荷開始前に通知する。GPUの現在の用途、常駐モデル、待ち行列をGUIに表示する。
- QwenのQ8全5ファイルは約188GB。ファイルサイズはVRAM必要量ではない。StrataのGPUキャッシュ・RAM常駐予算・SSD参照を実測して設定する。
- Strata標準setupは指定のorcarouter Q8を直接選択できない。native packの`--compat-bf16`経路を検証し、互換変換と精度上の差を記録する。低bitへ暗黙に変更しない。

## 公開に向けた管理

現在のGitHubリポジトリは非公開。将来公開するため、モデル・作品・データセット・会話・APIキー・個別設定をソースと分離し、固定リビジョン、取得手順、依存ライセンス、設定例、検証結果を管理する。公開への切替自体は今回行わない。

## 確認結果と限界

- A1 Q8本体・projector、Qwen Q8全5ファイルの取得とSHA256照合を完了。A1は65,536 context設定で常駐し、実APIでツール呼び出しと画像入力を確認した。画像説明には読順・動作の誤認があり、自動品質判定は未確立。
- StrataをCUDA 13 / sm_120でビルドし、Q8 native packとMTPを準備した。262,144 contextの設定は作成済み。**Qwen実機推論・速度・長文の品質は未検証**。空きRAM 88GiB以上が必要で、利用者によるVM停止を待っている。起動ごとのモデル再ロードがコーディングの待ち時間になる点も未測定。
- 実A1からGemmaへ設定・場所・ページ配分・プロンプトを順に依頼し保存した。Kroma＋Style LoRA強度0.6で2コマ生成し、縦書き文字を重ねてSVG/HTMLを出力。試験は`.test-output/resident-workflow-1791213162976/`。A1は題名を「出発の朝」から「出航の朝」に取り違え、余分な再制作も行った。工程は完走したが意味的な品質確認は利用者のレビューを要する。
- 出力の目視ではコマ間の衣装の変化と、試験用の固定座標に置いた吹き出しによる顔の隠れを確認した。Gemmaが2コマ目の衣装説明を省いたため、人物・場所の固定説明を作画ツールが各コマへ付加するよう修正した。付加されることは回帰試験済みだが、この修正後の実画像による品質比較は未実施。吹き出し位置はGUIで調整する。
- Gemma・Kreaの実処理中と終了後にA1のPIDが変わらないことを確認。Krea終了後はGPUモデルが解放され、CUDAコンテキスト等は約728MiB残った。GPUキューはプロセス間の排他、空きメモリ待ち、キャンセル、所有プロセス終了を扱う。生成サーバーをNixシェル経由で起動した際のPython参照も修正した。
- Krea、H3、長尺Comfy、キャプション、LoRA学習、編集の管理経路にGPUキューを接続した。H3/キャプション/学習の新しい待機経路は今回の実GPU生成・学習では再試験していない。Comfyの待機中キャンセルと失敗結果の保持はCPU模擬試験で確認。
- モデル/LoRA一覧、個別強度・用途、サムネイル登録、保存・再読込、未保存値の維持をブラウザーで確認。ギャラリーには動画作品のまとまりを追加し、既存動画もセッションごとにまとめる。
- 通常DSH GUIでも一覧表示を確認（モデルとLoRAの合計でKrea 31件、H3 16件）。GPUカードのA1状態表示と、旧Qwen 27Bを明示した既存セッションのA1への移行を確認。36件のNode回帰、GPU/Comfyの6件とモデルAPIライフサイクル1件、ブラウザー試験、実DSH模擬API試験、リポジトリ監査14項目が成功。
- **H3の新規LoRA学習は未統合**。Kreaは既存の1ステップ学習記録があり、本番の長時間学習は未検証。GPUキューの追加を学習機能の追加や品質保証と混同しない。

共通キューは管理されたプロセス間の同時実行を防ぐ。外部プロセスが後からVRAMを確保することや実行中の予想外のメモリ増加まで保証するものではない。VM・他アプリを勝手に停止しない。メモリ不足は状態とエラーで返す。
